## Why this, and why now
0.8.2's release (2026-10-31 → 2026-11-01) hit two problems in the release pipeline. Neither is in
crustyimg's code.
1. **The Apple Silicon build runs on a retired runner.** cargo-dist 0.32.0 (`dist-workspace.toml`)
   put `build-local-artifacts (aarch64-apple-darwin)` on `macos-14`. GitHub failed it twice during
   a scheduled brownout (run `41251779509`, attempts 1 and 2; the job's annotation names the
   brownout) and **retired `macos-14` on 2026-11-02**. Attempt 3, outside the window, worked. **The
   next tag will fail every time** until the runner changes. See
   <https://github.com/actions/runner-images/issues/13518>.
2. **npm is published by hand.** No workflow publishes `crustyimg-wasm`; the maintainer runs
   `just wasm-npm-publish` from a tag worktree after `npm login`. The maintainer wants a workflow,
   so there is no login to remember, using **npm trusted publishing** (OIDC from GitHub Actions, no
   stored token).
   - ⚠ **DEC-067 forbids this today:** "`npm publish` is never run by a recipe, a script, or an
     agent", and it rejected "a CI release job" *for now* because a one-keystroke path to an
     irreversible publish is a hazard. The maintainer's position: **pushing the tag is the
     deliberate act**, the same as crates.io (`publish-crates.yml`) and Homebrew already. Frame the
     amendment; do not treat DEC-067 as already changed.
3. **The brownout also showed a partial release.** crates.io (`publish-crates.yml`, on the tag
   push) and npm (by hand) published 0.8.2 while the GitHub Release and Homebrew did not exist. That
   stayed true for about two hours. Whether every publish should wait for the binaries is in scope
   for this frame to weigh.

This is release infrastructure, filed under STAGE-054 because that stage carries the 0.8.x line.
It has no version of its own: it must land before the **next** tag, whatever that is.

## What is known (reproduce it, don't trust it)
- `dist-workspace.toml`: `cargo-dist-version = "0.32.0"`, four targets, `publish-jobs =
  ["homebrew"]`, no `github-custom-runners`.
- `.github/workflows/release.yml` is generated by `dist`; its matrix comes from the `plan` job. The
  `plan` job's output for run `41251779509` names the runner for each target. Read it: which
  runner did `x86_64-apple-darwin` get, and is that image also on a retirement schedule?
- `.github/workflows/publish-crates.yml` (327 B) runs `cargo publish --locked` on `v*` tags.
- `.github/workflows/pages.yml` already builds the size-profiled `.wasm` in CI (wasm32 target,
  wasm-pack, `just wasm-build`, DEC-066), so the toolchain setup exists.
- `justfile` `wasm-npm-publish` → `wasm-npm-smoke` → `wasm-npm-pkg` → `wasm-build`: the size
  profile, a tarball smoke test, a version guard (pkg vs `Cargo.toml`) and a dirty-tree refusal,
  then `cd pkg && npm publish`.
- `scripts/wasm-npm-finalize.mjs` writes `pkg/package.json`, and rejects lifecycle scripts.

## Questions this frame must answer
1. **The runner fix.** What is the smallest change that moves `aarch64-apple-darwin` off
   `macos-14` (for example `[dist.github-custom-runners]` with `macos-15`)? Regenerate
   `release.yml` with the **same** `dist` version, and show the diff is only the runner. Does any
   other target sit on an image with a retirement date? Would upgrading `dist` instead be better,
   and what would it change?
2. **Proving it without publishing.** A real `v*` tag publishes to crates.io (irreversible). How do
   we prove the new `release.yml` builds all four targets **before** the next real tag? Read what
   cargo-dist offers (`pr-run-mode`, plan/upload on a PR, `workflow_dispatch`) and recommend one.
   A pre-release tag is **not** acceptable if it fires `publish-crates.yml` or npm.
3. **npm trusted publishing: the facts.** From npm's own docs, and the CLI version on the runner:
   - the minimum npm CLI and Node versions, and the `permissions: id-token: write` the job needs;
   - what `package.json` must contain (`repository` matching `jysf/crustyimg` for provenance), and
     whether `wasm-npm-finalize.mjs` writes it today;
   - the one-time setting the maintainer makes on npmjs.com (package → Trusted publisher → GitHub
     Actions: owner, repo, workflow file name, environment if any);
   - whether token publishing can then be turned off for the package, and whether to recommend it.
   Cite each fact from the doc page, quoting at most one short phrase.
4. **Where the npm publish runs, and when.**
   - Option A: its own workflow on `v*` tags, like `publish-crates.yml`.
   - Option B: a cargo-dist custom publish job (`publish-jobs = ["homebrew", "./publish-npm"]`),
     which runs only after `host` has created the GitHub Release.
   - Weigh moving crates.io the same way, so nothing publishes unless every binary built. What does
     a failure halfway through look like in each option, and how is it re-run?
   - The trusted-publisher setting names one workflow file. Does Option B's reusable-workflow call
     satisfy it? Check.
5. **The publish path stays guarded.** The job must still run the size-profiled build and the smoke
   test, and must refuse a `pkg/` version that differs from the tag. Can it call
   `just wasm-npm-publish` unchanged (it refuses a dirty tree; does CI leave the tree clean)? If
   not, name the smallest change. The version guard compares against `Cargo.toml`. Add a tag check?
6. **DEC-067.** Draft the amendment's rule in one or two sentences: who decides a publish (the tag
   push), what still never publishes (any agent, any recipe run by hand in CI outside the tag
   path). Or say why a new DEC-111 is cleaner.
7. **Docs.** `RELEASING.md` steps 7–8 and its channel list, and any doc that says npm is published
   by hand. List each sentence that changes.
8. **Size and scope.** Expect [S] or low [M]. STAGE-054 already has an entry "No CI job runs the
   wasm round-trip tests". It shares the wasm toolchain. Say whether to fold it in or leave it
   separate, with a reason; do not fold it in silently.
